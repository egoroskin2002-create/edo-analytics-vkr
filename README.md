
EDO Analytics VKR
Система аналитики электронного документооборота (ЭДО), построенная на Apache Kafka и ClickHouse. Проект охватывает весь путь данных: от генерации событий и их передачи через Kafka до хранения и аналитической обработки в ClickHouse.

О проекте
Цель проекта — собрать прототип системы, которая принимает события электронного документооборота и позволяет анализировать их практически в реальном времени.

Для проверки работы конвейера используются синтетические данные. Python-скрипты создают события и сохраняют их в JSONL-файлы, после чего отдельный загрузчик отправляет их в Kafka. ClickHouse получает сообщения из Kafka, сохраняет их в распределённом кластере и предоставляет таблицы для аналитических запросов. Для работы с результатами также настроен Apache Superset.

Основные этапы обработки данных:

Генерация событий и сохранение их в JSONL-файлах.
Проверка структуры данных и целостности жизненных циклов документов.
Отправка событий из файлов в Kafka.
Получение и хранение событий в ClickHouse.
Выполнение аналитических запросов и подготовка данных для визуализации.

Конфигурация ClickHouse
Кластер edo_cluster состоит из двух шардов, в каждом из которых настроено по две реплики.

Шард	Реплика 1	Реплика 2
1	ch-shard1-replica1	ch-shard1-replica2
2	ch-shard2-replica1	ch-shard2-replica2
Основная база данных — edo_analytics.

В ней используются следующие таблицы и объекты:

document_events_local — локальная таблица на движке ReplicatedMergeTree.
document_events — распределённая таблица на движке Distributed.
kafka_document_events — источник событий на движке Kafka.
kafka_document_events_mv — материализованное представление, которое передаёт полученные из Kafka события в таблицу для аналитики.
Распределение данных между шардами выполняется по хешу DocumentId. Благодаря этому события одного документа попадают в один и тот же шард.

Локальные таблицы реплицируются между двумя репликами соответствующего шарда.

Модель события
Каждая запись в наборе данных описывает отдельное событие из жизненного цикла документа. У одного документа может быть несколько событий с одинаковым DocumentId; при этом каждое событие имеет собственный EventId.

Поле	Тип ClickHouse	Назначение
EventTime	DateTime	Время возникновения события
EventId	UUID	Идентификатор события
DocumentId	UUID	Идентификатор документа
RegionId	LowCardinality(String)	Регион филиала, в котором произошло событие
BranchId	LowCardinality(String)	Филиал, в котором произошло событие
SourceBranchId	LowCardinality(String)	Филиал отправления документа
TargetBranchId	LowCardinality(String)	Филиал назначения документа
EventType	LowCardinality(String)	Тип события
DocumentType	LowCardinality(String)	Тип документа
PayloadSize	UInt64	Размер полезной нагрузки в байтах
DurationMs	UInt32	Длительность этапа в миллисекундах
RegionId и BranchId описывают место, в котором произошло конкретное событие. SourceBranchId и TargetBranchId задают маршрут документа и не меняются на протяжении его жизненного цикла.

Генерация синтетических данных
Генератор находится в файле scripts/event_generator.py. Он создаёт синтетические события ЭДО и записывает их в JSONL-файлы: одна строка файла соответствует одному JSON-объекту.

Жизненный цикл документа
Для каждого документа генерируются четыре последовательных события:

DocumentCreated — документ создан.
DocumentSent — документ отправлен.
DocumentReceived — документ получен.
DocumentSigned или DocumentRejected — документ подписан или отклонён.
У всех четырёх событий одного документа одинаковый DocumentId, но разные EventId. Маршрут документа (SourceBranchId и TargetBranchId) сохраняется на всех этапах.

Для событий создания и отправки RegionId и BranchId соответствуют исходному филиалу. Для получения и завершения обработки — филиалу назначения.

У первого события DurationMs равен нулю. Для следующих событий длительность рассчитывается как интервал между этапами в миллисекундах. Значение EventTime записывается в формате YYYY-MM-DD HH:MM:SS с точностью до секунды.

Параметры генерации
Период событий: с 1 января 2022 года по 31 декабря 2025 года.
Вероятность подписания: 78%.
Вероятность отклонения: 22%.
Типы документов: Invoice, Contract, Act, Waybill.
Количество регионов: 3.
Количество филиалов: 9.
Запуск генератора
Команды выполняются из корневого каталога проекта. Для работы используется виртуальное окружение Python.

Создать набор размером 500 MiB:

.venv/bin/python scripts/event_generator.py --size-mib 500
Создать набор размером 4 GiB:

.venv/bin/python scripts/event_generator.py --size-mib 4096
Создать набор размером 10 GiB (значение по умолчанию):

.venv/bin/python scripts/event_generator.py
Каждый запуск создаёт новый каталог в data/jsonl/ с уникальным именем вида dataset_<timestamp>_<random>. Уже существующие наборы не перезаписываются.

Файлы внутри набора называются events_0001.jsonl, events_0002.jsonl и так далее. Целевой размер одного файла — около 500 MiB.

Ротация файлов происходит между жизненными циклами документов. Поэтому события одного документа не оказываются в разных файлах. Генератор заканчивает работу после записи полного жизненного цикла, когда общий объём достигает или немного превышает заданный размер.

Проверка корректности данных
За проверку данных отвечает scripts/validate_dataset.py.

Перед отправкой набора в Kafka рекомендуется запустить валидатор. Он проверяет не только корректность JSONL, но и то, что события каждого документа образуют полный и последовательный жизненный цикл.

Запуск проверки:

.venv/bin/python scripts/validate_dataset.py dataset_<имя_набора>
Валидатор проверяет, что:

каждая строка содержит корректный JSON-объект;
в каждой записи присутствуют ровно 11 ожидаемых полей;
у каждого документа есть четыре события;
у событий одного документа совпадает DocumentId;
EventId не повторяется внутри проверяемого жизненного цикла;
маршрут документа не меняется;
события расположены в правильном порядке;
все события одного документа находятся в одном файле.
Набор размером 4 GiB успешно прошёл проверку: ошибок валидации не обнаружено.

Передача данных в Kafka
За отправку событий отвечает scripts/kafka_producer.py. Загрузчик последовательно читает JSONL-файлы и передаёт содержащиеся в них события в Kafka.

Параметры подключения:

брокер: localhost:9093;
топик: edo-documents;
ключ сообщения: DocumentId;
подтверждение доставки: acks=all;
количество повторных попыток отправки: 5.
В качестве ключа сообщения используется DocumentId. Это позволяет Kafka направлять события одного документа по одному ключу.

Запуск загрузчика
Отправить весь набор:

.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора>
Ограничить количество отправляемых событий:

.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --limit 1000
Задать размер пакета:

.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --batch-size 1000
Ограничить скорость отправки:

.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --rate 1000
Настроить частоту вывода прогресса:

.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --progress-every 100000
Контроль загрузки и возобновление
Загрузчик сохраняет своё состояние в файле .kafka_checkpoint.json внутри каталога набора данных. Это позволяет продолжить отправку после остановки, не начиная обработку с самого начала.

В checkpoint записываются:

идентификатор набора данных;
индекс текущего файла;
номер последней подтверждённой строки.
Файл состояния сохраняется через атомарную замену временного файла. При запуске с параметром --resume загрузчик проверяет, что checkpoint относится к выбранному набору, и продолжает чтение с сохранённой позиции.

Пример возобновления загрузки:

.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --resume
Checkpoint обновляется после подтверждения доставки сообщений брокером. Если программа аварийно завершится между подтверждением сообщения и сохранением checkpoint, последнее сообщение может быть отправлено повторно. Таким образом, используется модель доставки как минимум один раз (at-least-once); гарантия exactly-once не предоставляется.

После начала загрузки не рекомендуется изменять содержимое файлов набора данных.

Параметры командной строки
Параметр	Назначение
dataset	Имя каталога с JSONL-файлами
--limit	Ограничение количества отправляемых событий
--batch-size	Размер пакета отправки
--progress-every	Частота вывода прогресса
--rate	Максимальная скорость отправки, событий в секунду
--resume	Продолжение загрузки по сохранённому checkpoint
Kafka
Для передачи событий используется топик edo-documents. Его создание выполняет вспомогательный сервис kafka-init при запуске инфраструктуры.

Текущие параметры топика:

количество партиций: 1;
replication factor: 1.
Контейнеры внутри Docker-сети обращаются к брокеру по адресу kafka:9092. Для подключения с хоста используется localhost:9093.

Получение событий в ClickHouse настроено через Kafka Engine и материализованное представление. Kafka Engine читает сообщения из edo-documents в таблицу kafka_document_events, а материализованное представление передаёт их в document_events.

Apache Superset
Для работы с аналитическими данными в проект добавлен Apache Superset версии 6.1.0. Он запускается в отдельном Docker-контейнере и подключается к ClickHouse по внутренней Docker-сети.

Чтобы Superset мог работать с ClickHouse, при сборке собственного образа устанавливается Python-пакет clickhouse-connect. Для этого в проекте используются два файла:

Dockerfile.superset — описывает образ на основе apache/superset:6.1.0 и установку драйвера;
requirements-superset.txt — содержит зависимость clickhouse-connect>=0.13.0.
Драйвер устанавливается в виртуальное окружение Superset (/app/.venv), из которого запускается само приложение.

Сборка образа:

DOCKER_BUILDKIT=0 docker compose build superset
Запуск или обновление контейнера Superset:

docker compose up -d --no-deps superset
В Superset настроено подключение к базе edo_analytics на узле ch-shard1-replica1 через HTTP-порт 8123. Для подключения используется SQLAlchemy URI следующего вида:

clickhousedb://<username>:<password>@ch-shard1-replica1:8123/edo_analytics
Вместо заполнителей указываются учётные данные ClickHouse. Пароль и другие секреты не должны попадать в README или Git.

Для работы с данными в Superset добавлен Dataset на основе распределённой таблицы document_events. Она используется как точка доступа к данным обоих шардов кластера.
