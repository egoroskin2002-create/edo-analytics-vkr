# EDO Analytics VKR

Система сквозной real-time аналитики корпоративного электронного документооборота (ЭДО) на основе Apache Kafka и ClickHouse.

## О проекте

Проект предназначен для приёма, хранения и аналитической обработки событий электронного документооборота в режиме, близком к реальному времени.

Python используется для генерации синтетических событий ЭДО и передачи подготовленных данных в Kafka. Kafka обеспечивает передачу событий, ClickHouse — распределённое хранение и выполнение аналитических запросов, Apache Superset предусмотрен для визуализации данных.

Работа с данными разделена на этапы:

1. Генерация событий и запись в JSONL-файлы.
2. Проверка корректности и целостности сгенерированных данных.
3. Передача событий из JSONL-файлов в Kafka.
4. Обработка и хранение событий в ClickHouse.
5. Аналитическая обработка и визуализация.

## Конфигурация ClickHouse

Кластер `edo_cluster` включает два шарда с двумя репликами в каждом.

| Шард | Реплика 1            | Реплика 2            |
| ---- | -------------------- | -------------------- |
| 1    | `ch-shard1-replica1` | `ch-shard1-replica2` |
| 2    | `ch-shard2-replica1` | `ch-shard2-replica2` |

Основная база данных: `edo_analytics`.

Основные таблицы:

- `document_events_local` — локальная таблица на движке `ReplicatedMergeTree`.
- `document_events` — распределённая таблица на движке `Distributed`.
- `kafka_document_events` — источник событий на движке Kafka.
- `kafka_document_events_mv` — материализованное представление для загрузки событий в распределённую таблицу.

Распределение данных между шардами выполняется по хешу `DocumentId`. Поэтому события одного документа направляются в один и тот же шард.

Локальные таблицы реплицируются между соответствующими репликами каждого шарда.

## Модель события

Каждая запись представляет отдельное событие жизненного цикла документа. Один документ может иметь несколько событий с одинаковым `DocumentId`; каждое событие получает собственный `EventId`.

| Поле             | Тип ClickHouse           | Назначение                                  |
| ---------------- | ------------------------ | ------------------------------------------- |
| `EventTime`      | `DateTime`               | Время возникновения события                 |
| `EventId`        | `UUID`                   | Идентификатор события                       |
| `DocumentId`     | `UUID`                   | Идентификатор документа                     |
| `RegionId`       | `LowCardinality(String)` | Регион филиала, в котором произошло событие |
| `BranchId`       | `LowCardinality(String)` | Филиал, в котором произошло событие         |
| `SourceBranchId` | `LowCardinality(String)` | Филиал отправления документа                |
| `TargetBranchId` | `LowCardinality(String)` | Филиал назначения документа                 |
| `EventType`      | `LowCardinality(String)` | Тип события                                 |
| `DocumentType`   | `LowCardinality(String)` | Тип документа                               |
| `PayloadSize`    | `UInt64`                 | Размер полезной нагрузки в байтах           |
| `DurationMs`     | `UInt32`                 | Длительность этапа в миллисекундах          |

`RegionId` указывает регион филиала, в котором произошло событие. `BranchId` обозначает филиал, где произошло конкретное событие. `SourceBranchId` и `TargetBranchId` описывают маршрут документа и остаются неизменными на протяжении его жизненного цикла.

## Генерация синтетических данных

Генератор реализован в файле `scripts/event_generator.py`.

Он создаёт синтетические события электронного документооборота в формате JSONL. Каждая строка содержит один JSON-объект, соответствующий модели события.

### Жизненный цикл документа

Каждый документ представлен четырьмя последовательными событиями:

1. `DocumentCreated` — создание документа.
2. `DocumentSent` — отправка документа.
3. `DocumentReceived` — получение документа.
4. `DocumentSigned` или `DocumentRejected` — подписание или отклонение документа.

Все четыре события имеют одинаковый `DocumentId` и собственные `EventId`. Поля `SourceBranchId` и `TargetBranchId` сохраняют маршрут документа на протяжении всего жизненного цикла.

Для событий создания и отправки `RegionId` и `BranchId` соответствуют исходному филиалу. Для событий получения и завершения обработки они соответствуют филиалу назначения.

`DurationMs` для первого события равен нулю. Для последующих событий значение рассчитывается по интервалу между этапами в миллисекундах. `EventTime` сохраняется в формате `YYYY-MM-DD HH:MM:SS` с точностью до секунды.

### Параметры генерации

- Период событий: с 1 января 2022 года по 31 декабря 2025 года.
- Вероятность подписания: 78%.
- Вероятность отклонения: 22%.
- Типы документов: Invoice, Contract, Act, Waybill.
- Количество регионов: 3.
- Количество филиалов: 9.

### Запуск генератора

Команды выполняются из корневого каталога проекта с использованием виртуального окружения Python.

Создание набора размером 500 MiB:

```bash
.venv/bin/python scripts/event_generator.py --size-mib 500
```

Создание набора размером 4 GiB:

```bash
.venv/bin/python scripts/event_generator.py --size-mib 4096
```

Создание набора размером 10 GiB:

```bash
.venv/bin/python scripts/event_generator.py
```

При каждом запуске создаётся новый каталог в `data/jsonl/` с уникальным именем вида `dataset_<timestamp>_<random>`. Ранее созданные наборы не перезаписываются.

Файлы называются `events_0001.jsonl`, `events_0002.jsonl` и далее. Целевой размер одного файла составляет около 500 MiB.

Ротация выполняется только между жизненными циклами документов, поэтому события одного документа не разделяются между файлами. Генерация завершается после записи полного жизненного цикла документа, когда общий объём достигает или превышает заданный размер. Фактический объём может немного превышать целевой.

## Проверка корректности данных

Валидатор реализован в файле `scripts/validate_dataset.py`.

Перед передачей набора в Kafka рекомендуется проверить формат JSONL и целостность жизненных циклов.

Запуск проверки:

```bash
.venv/bin/python scripts/validate_dataset.py dataset_<имя_набора>
```

Проверяются следующие условия:

- каждая строка является корректным JSON-объектом;
- каждая запись содержит ровно 11 ожидаемых полей;
- каждому документу соответствуют четыре события;
- `DocumentId` одинаков для всех событий одного документа;
- `EventId` не повторяется внутри проверяемого жизненного цикла;
- маршрут документа не меняется в пределах жизненного цикла;
- события следуют в правильном порядке;
- все события одного документа находятся в одном файле.

Резуль**тат:** проверка набора завершилась успешно. Все проверенные события соответствуют ожидаемой структуре, а жизненные циклы документов прошли проверку целостности.

## Передача данных в Kafka

Загрузчик реализован в файле `scripts/kafka_producer.py`.

Он последовательно читает JSONL-файлы и отправляет события в Kafka.

Параметры подключения:

- брокер: `localhost:9093`;
- топик: `edo-documents`;
- ключ сообщения: `DocumentId`;
- подтверждение доставки: `acks=all`;
- повторные попытки отправки: `5`.

Использование `DocumentId` в качестве ключа сообщения позволяет сохранять принадлежность событий одного документа к одному ключу Kafka.

### Запуск загрузчика

Полная отправка набора:

```bash
.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора>
```

Отправка с ограничением количества событий:

```bash
.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --limit 1000
```

Настройка размера пакета:

```bash
.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --batch-size 1000
```

Ограничение скорости отправки:

```bash
.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --rate 1000
```

Настройка частоты вывода прогресса:

```bash
.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --progress-every 100000
```

### Контроль загрузки и возобновление

Загрузчик поддерживает checkpoint — файл состояния `.kafka_checkpoint.json`, который хранится в каталоге соответствующего набора данных.

Checkpoint содержит:

- идентификатор набора данных;
- индекс текущего файла;
- номер последней подтверждённой строки.

Сохранение выполняется атомарной заменой временного файла. При использовании `--resume` загрузчик проверяет идентификатор датасета и продолжает обработку с сохранённой позиции.

Пример возобновления:

```bash
.venv/bin/python scripts/kafka_producer.py dataset_<имя_набора> --resume
```

Checkpoint фиксирует подтверждённую брокером доставку. При аварийном завершении между подтверждением сообщения и сохранением checkpoint возможна повторная отправка последнего сообщения. Поэтому механизм обеспечивает доставку как минимум один раз (at-least-once), но не гарантирует exactly-once.

Изменять содержимое файлов датасета после начала загрузки не рекомендуется.

### Параметры командной строки

| Параметр           | Назначение                                  |
| ------------------ | ------------------------------------------- |
| `dataset`          | Имя каталога с JSONL-файлами                |
| `--limit`          | Ограничение количества отправляемых событий |
| `--batch-size`     | Размер пакета отправки                      |
| `--progress-every` | Частота вывода прогресса                    |
| `--rate`           | Максимальная скорость отправки, событий/сек |
| `--resume`         | Возобновление по сохранённому checkpoint    |

## Kafka

Для передачи событий используется топик `edo-documents`. Его создание автоматизировано сервисом `kafka-init`.

Текущие параметры топика:

- число партиций: `1`;
- replication factor: `1`.

Внутренний адрес брокера для контейнеров: `kafka:9092`.

Адрес для подключения с хоста: `localhost:9093`.

Интеграция Kafka с ClickHouse настроена через Kafka Engine и материализованное представление. События из топика поступают в `kafka_document_events`, после чего материализованное представление передаёт их в `document_events`.
